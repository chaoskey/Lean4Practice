### 02-4 讲义：`?m.7` 的编号与「类型推断的边界」讲得不够（2026-09-19，已修正）

用户在订正完 02-4 习题后**继续追问**（这是本课最有价值的一个问题）：

> 「`#check fun x y => x + y` 打印的 `(x : ?m.7) → _`，其中 `.7` 从何而来？后面 `-> _` 又是为何？」

- **先澄清事实**：Lean 打的**不是** `-> _`（那个 `_` 是用户自己写在注释里的简写）。原文是
  `fun x y => x + y : (x : ?m.7) → (y : ?m.9 x) → ?m.10 x y`。
- **编号规律（实测）**：换表达式就变（`x + y` → `?m.7 / ?m.9 / ?m.10`；`x + y + z` → `?m.8 / ?m.15 / ?m.16 / ?m.18`），
  但**同一个表达式重复跑，编号稳定不变**（连跑三次完全一样）→ 它是「待定」的**创建序号**，
  **不是**行号、不是错误码、也不是随机数。
  最直接的证据：**只要多给一点线索**（写成 `(fun x y => x + y) 3`），待定就**全部被定下来**，
  输出变成干净的 `Nat → Nat`——说明那些待定本来都存在，只是被解出来了。
- **`?m.9 x` 后面那个 `x`**：表示这个待定**可能依赖 `x`**——这正是「依赖类型」这个名字的字面来源（归 **2-9**）。
- ⚠️ **我的讲义原来有一句是错的**：「具体编号每次运行可能不同」——**实测是稳定的**。
  已改正，并在讲义第 4 节新增一小节「`?m.7` 是什么？后面为什么跟着 `x`？」专门回答这两个问题；
  同时按 D14 第 3 条把「依赖类型」标为本课不引入（归 2-9）。

> **教训**：用户能问出「编号从哪来」，说明我原来那句「大意是……编号可能不同」是**糊过去的**——
> 只要材料里出现一个我**没有实际跑过**的细节（编号到底稳不稳定），就可能写错。
> **凡在材料里断言的现象，都要当场实测。**

## 检查命令

### 推荐：用检查脚本（只敲 ASCII，不用碰中文文件名）

```bash
bash TPIL/check.sh 02-2
```

它会**把这一课的示例和习题都跑一遍**，并直接给结论：

| 输出 | 意思 |
|---|---|
| `✅ 验收通过` | 习题：无编译错误，且没有 `sorry` 占位 —— **做完了** |
| `⏳ 还没做完：还有 N 处 sorry 占位` | 正常中间状态，继续做 |
| `❌ 有编译错误，先修掉` | 有问题 |
| `✅ 干净（零警告、零错误）` | 示例文件正常 |
| `⚠️ 这个文件本应零警告零错误` | 示例文件出问题了（那是我的责任） |

不带参数运行会列出**所有可用的课号**：

```bash
bash TPIL/check.sh
```

> 💡 为什么要用脚本：课号是纯 ASCII（如 `02-2`），而**文件名含中文**，
> 手敲容易字符错位。用它就不必碰中文文件名了。

### 手动检查（想自己看输出时）

```bash
lake env lean TPIL/02-2-习题.lean        # 换成当前习题文件
```

**⚠️ `sorry` 只是 warning，退出码仍是 0**——「能通过检查」**不代表**题做完了。

真正的验收（两条都要过）：

```bash
lake env lean TPIL/02-2-习题.lean && ! grep -qE '^[[:space:]]*sorry[[:space:]]*$' TPIL/02-2-习题.lean
```

即 **① 无编译错误 ② 文件里不再有「整行就是 `sorry`」的占位**。

> **所以习题里的 `sorry` 一律单独占一行**——否则验收脚本检不出来。
> ⚠️ 也别用 `grep -n 'sorry'` 这种简单写法：它会把**注释里提到 `sorry` 的文字**也算作占位。
