## 1. 本课的一句话

上一课（3-1）说清了：**命题就是类型，证明就是项**。

本课**动手**：**写你的第一个证明**。你会发现它**长得和写函数一模一样**：

```lean
variable {p q : Prop}

theorem t1 : p → q → p := fun hp : p => fun _ : q => hp
```

**读法**（本课核心，逐段拆）：

| 这一段 | 它在说 |
|---|---|
| `theorem t1 :` | 我要**造一个项**，它的类型是…… |
| `p → q → p` | ……**这个命题**（也就是**这个类型**） |
| `:= fun hp : p =>` | 「**假设 `p` 成立**」（名字叫 `hp`）——**引入一个前提** |
| `fun _ : q =>` | 「**再假设 `q` 成立**」（这个假设**用不上**，见 §4） |
| `hp` | **交出 `hp`** —— 这就完成了证明 |

> 💡 **一句话**：**「假设……则……」在 Lean 里就是 `fun`**。这**不是巧合**——3-1 的 Curry–Howard 同构说的就是这个。

## 2. `theorem` 命令：它就是 `def` 的另一种写法

原文（我翻译）：

> 在「命题即类型」的范式里，**只涉及 `→` 的定理可以用 lambda 抽象和函数应用来证明**。
> 在 Lean 里，**`theorem` 命令**用来引入一个新定理。
>
> 注意 **`theorem` 命令其实就是 `def` 命令的一个版本**：
> 在「命题与类型对应」之下，**证明定理 `p → q → p` 和「定义出那个类型的一个元素」完全是同一件事**。
> **对内核的类型检查器来说，两者没有区别。**

**与 `fun x : α => fun y : β => x` 对照**（原文原话）：

> 把这个证明和类型为 `α → β → α` 的表达式 `fun x : α => fun y : β => x` **比较一下**
> （其中 `α`、`β` 是**数据类型**）……**证明 `t1` 的形状完全一样，唯一的区别是 `p`、`q` 是 `Prop` 的元素而不是 `Type` 的元素。**

直觉（原文）：

> 我们的 `p → q → p` 的证明**假设 `p` 和 `q` 为真**，然后用**第一个假设**（平凡地）确立结论 `p` 为真。

---

## 3. 写下来的四种等价写法

**同一件事，几种写法**（**都产生同一个项**）：

```lean
variable {p q : Prop}

-- ① 层层 fun —— 就是 §1 那个 `t1`（这里不重复声明，免得重名）

-- ② 参数写到冒号左边（和 def 一样）
theorem t1c (hp : p) (_hq : q) : p := hp

-- ③ 多个参数挤在一个 fun 里
theorem t1d : p → q → p := fun hp _ => hp
```

（**上面三种我都会在示例里跑一遍**，你可以用 `#print` 看到它们**变成同一个东西**。）

> ⚠️ **② 那种写法要留意 §4 的 warning**——`_hq` 前面的下划线是**故意**的。

---

## 4. ⚠️ 一个你一定会遇到的 warning

先看这一段（**故意写成有问题的**）：

```
theorem t1 : p → q → p := fun hp : p => fun hq : q => hp
-- warning: Variable name `hq` is not explicitly referenced.
```

**为什么**：`p → q → p` 的证明**根本用不上** `q` 的证明（结论就是 `p`），
可你**给那个参数起了名字** `hq`，于是 Lean 的 linter 提醒你：「这个名字没被引用」。

**这不是错误**（文件照样编译、退出码还是 0），但**看着不干净**。原文的写法里也带着它——
原文的示例文件顶部写了 `set_option linter.unusedVariables false` 来**关掉这个提示**。

**三条修法（实测都有效，零 warning）**：

| 写法 | 效果 |
|---|---|
| `fun _ : q => hp` | **不给它名字**（最推荐） |
| `fun _ => hp` | 同上（类型让 Lean 推） |
| `fun _hq : q => hp` | **名字前加下划线**（Lean 的提示就是这么建议的） |
| `set_option linter.unusedVariables false` | **整体关掉这个 linter**（原文的做法） |

> 📌 **一句话**：**用不上的参数，名字前加下划线 `_`**——这个习惯从本课起会一直用到。

---

## 5. `theorem` 与 `def` 的**实用差别**（原文四点）

原文说，虽然对内核来说两者没区别，但**实用上**有几点不同（我翻译）：

1. **正常情况下，永远不需要展开一个定理的「定义」**——
   由 **proof irrelevance**（3-1 学的），**同一个定理的任意两个证明都是按定义相等的**。
2. 一个定理的证明写完之后，**我们通常只需要知道「这个证明存在」**，**不关心它是什么**。
   因此 Lean 把证明标成 **irreducible（不可展开）**，作为给推演器的提示：处理文件时**一般不必展开它们**。
3. 事实上，**Lean 通常能并行地处理和检查各个证明**——因为判断一个证明是否正确，**不需要知道另一个证明的细节**。
4. ⚠️ **关于 section 变量**（`variable`，02-7 学的）：
   > 在**定义**（`def`）里被**引用到**的 section 变量，会被自动加成参数；
   > 但**定理**（`theorem`）**只把「出现在定理的类型里的」那些**变量加成参数。
   > **这是因为：一个命题「怎么被证明」不应该影响「被证明的是什么」。**

5. ⚠️ **`theorem` 的语句必须是「命题」**（这一条**原文没提**，是我实测出来的）：
   **`theorem` 只接受类型为 `Prop` 的语句**；`def` **没有**这个限制。实测对照
   （两段都**没有**声明 `p`、`q`，Lean 把它们自动绑成了**任意类型** `Sort u`）：

   ```
   theorem bad : p' → q' → p' := fun hp : p' => fun _ : q' => hp
   -- error: type of theorem `bad` is not a proposition
   --        {p' : Sort u_1} → {q' : Sort u_2} → p' → q' → p'

   def good : p → q → p := fun hp : p => fun _ : q => hp
   -- ✅ def good.{u_1, u_2} : {p : Sort u_1} → {q : Sort u_2} → p → q → p
   ```

   **含义**：**`theorem` 就是「专门用来证命题」的 `def`**——这是它与 `def` **最实质**的一条差别。

   > ⚠️ **这也解释了本课代码块的一个要求**：凡是 `theorem`，**上面必须先写 `variable {p q : Prop}`**。
   > 不写的话，`p`、`q` 会被当成**任意类型**（`Sort u`），`theorem` 就会报
   > `type of theorem … is not a proposition`。**（讲义自身的代码块就是这么修的。）**

**第 4 点值得慢慢读**——它正是本课与 3-1 的呼应：

| | 加哪些 section 变量当参数 |
|---|---|
| `def` | **定义体里用到的**都加 |
| `theorem` | **只在类型里出现的**才加 |

**为什么这样设计**：证明是「怎么证」的事，**不该泄漏到「证的是什么」里去**。

## 6. `#print`：看看 Lean 到底记下了什么

实测（`t1` 就是 **§1** 定义的那个）：

```lean
#print t1
```

实测输出：

```
theorem t1 : ∀ {p q : Prop}, p → q → p :=
fun {p q} hp x => hp
```

**两点**：

1. **类型写成了 `∀ {p q : Prop}, p → q → p`** —— 出现了 **`∀`**！
   > ⚠️ **`∀` 是什么**：它**就是 02-9 学的「依赖函数类型」** `(x : α) → β x` 的**另一种写法**。
   > 所以上面那行读作：「**对任意**命题 `p q`，都有 `p → q → p`」。
   > （`∀` 的完整讲解在**第 4 章**；本课你只要**认得**它、知道**它和 `→` 是一家人**。）
2. **证明体写成了 `fun {p q} hp x => hp`** —— 注意那个 **`x`**：
   我写的是 `fun _ : q =>`，**没有给它名字**，于是 Lean 自己起了个**无法引用的名字** `x`。

## 7. `show … from …`：给最终的项**标上类型**

原文（我翻译）：

> 注意，lambda 抽象 `hp : p` 和 `hq : q` 可以看成证明中的**临时假设**。
> Lean 也允许我们用 **`show` 语句**显式地**指定最终项 `hp` 的类型**——写成这样：

```lean
variable {p q : Prop}

theorem t1e : p → q → p :=
  fun hp : p =>
  fun _ : q =>
  show p from hp
```

> **加上这样的额外信息可以提高证明的可读性，并帮助在写证明时发现错误。**
> **`show` 命令只做一件事：标注类型**——内部来说，我们见过的所有 `t1` 的写法**产生的是同一个项**。

**实测一个小发现**（`t1e` 就是本节上面定义的那个）：

```lean
#print t1e
```

实测输出：

```
theorem t1e : ∀ {p q : Prop}, p → q → p :=
fun {p q} hp x =>
  have this := hp;
  this
```

**`show p from hp` 内部变成了 `have this := hp; this`**——**`have` 是「引入辅助子步骤」**，
属 **3-7** 的内容；本课你只要知道：**`show … from …` 只是个「标注」，不改变证明本身**。

## 8. 把定理当函数用（应用）

既然定理就是「一个类型的项」，那它**当然可以像函数一样被应用**。原文的例子用了 `axiom`
（**本课不引入**，见 §11），我**换成把假设写成参数**——实测：

（`t1` 就是 **§1** 定义的那个。）

```lean
variable {p q : Prop}

theorem t2 (hp : p) : q → p := t1 hp

#check t2
```

实测输出：

```
t2 {p q : Prop} (hp : p) : q → p
```

**读法**：`t1 hp` 的意思是「**把定理 `t1` 应用到「`p` 成立」这个事实 `hp` 上**」——
于是得到「**`q → p`**」这个**新定理**。

> ⚠️ **实测的坑**：**不要**用 `variable (hp : p)` 来声明假设——
> 当 `p` 是隐式变量（`variable {p q : Prop}`）时，Lean 会报 **`Unknown identifier 'hp'`**。
> **把假设写成定理的参数**（`theorem t2 (hp : p) : …`）就行。

## 9. 泛化以后，能复用到**不同的命题对**上

原文（我翻译）：

> 如果 `p` 和 `q` 已经用 `variable` 声明过，**Lean 会自动帮我们泛化它们**。
> 这样泛化之后，我们就能把它应用到**不同的命题对**上，得到这个一般定理的**不同实例**。

实测（把参数都写到左边之后）：

```lean
variable (p q r s : Prop)
theorem t1' (p q : Prop) (hp : p) (_hq : q) : p := hp

#check t1' p q
#check t1' r s
#check t1' (r → s) (s → r)
```

实测（3 行）：

```
t1' p q : p → q → p
t1' r s : r → s → r
t1' (r → s) (s → r) : (r → s) → (s → r) → r → s
```

**看第 3 行**：`p` 和 `q` 可以是**任意命题**——连 **`r → s`**（一个蕴含式）都能当 `p`！
原文对此的评论（我翻译）：

> 再次利用「命题即类型」的对应，类型为 `r → s` 的变量 `h` 可以被看成**假设**、或者说**前提**：`r → s` 成立。

## 10. 一个综合例子：复合（原文的 `t2`）

原文给的例子（我翻译并改掉 `axiom` 部分）：

```lean
variable {p q r : Prop}
theorem comp (h₁ : q → r) (h₂ : p → q) : p → r :=
  fun h₃ : p =>
  show r from h₁ (h₂ h₃)
```

**它说的是**：**如果 `q → r` 且 `p → q`，那么 `p → r`**——这就是**「推理的传递性」**。

**读法（从里往外）**：

| 片段 | 意思 |
|---|---|
| `h₃ : p` | 假设 `p` 成立 |
| `h₂ h₃ : q` | 用 `p → q` 把 `p` 变成 `q` |
| `h₁ (h₂ h₃) : r` | 再用 `q → r` 把 `q` 变成 `r` |
| `show r from …` | 标注：我要交出的就是 `r` |

> 📌 原文还提了一个**排版建议**：**假设可以用数字下标**（`h₁`、`h₂`、`h₃`）——
> 打字方式是 `\1`、`\2`、`\3`（见 [`Unicode速查.md`](./Unicode速查.md)）。

## 12. 小结

本课记住四件事：

1. **`theorem` 就是 `def`**：证明定理 = **造出那个类型的项**；对内核来说两者没区别。
2. **证明的写法 = 函数的写法**：`fun hp : p => …` 就是「**假设 `p` 成立**」；
   `p → q → p` 的证明与 `α → β → α` 的函数**形状完全一样**。
3. **⚠️ 用不上的参数，名字前加下划线**（`_hq`）——否则会报 unused variable warning。
4. **`show … from …` 只做「标注」**；`#print` 能让你看到 Lean 记下的**真正形状**
   （类型写成 `∀ …`，证明体写成 `fun …`）。
